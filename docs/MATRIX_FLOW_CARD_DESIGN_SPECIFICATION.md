# PostSoma Kitchen · Matrix Flow Card 正式产品设计规范与标准

> **生效说明**：本文档为 PostSoma Kitchen `VisualRecipeV3.0` Matrix Flow Card 的**最终权威设计规范**。
> 本规范明确确立“流程速览”的产品定位，确立“完整数据—精简主图—详细说明”三层标准，并正式废止此前“为新手看图即会而在主图中大量灌水文字”的冲突设计。

---

## 一、产品定位与核心阅读方式

### 1. 目标受众与产品定位
Matrix Flow Card **面向已经具备基本烹饪经验、能够理解常见烹饪技法（如焯水、滑炒、焖炖、过油、勾芡、收汁）的用户**。

它的核心目的是：**用最简单、最凝练的视觉结构表达，让用户在一眼扫视间快速理解一整道菜的完整加工流程与物料流转。**

**主图是全局加工流程的“流程速览”，不承担详尽的新手基础教学。**

### 2. 核心阅读方式
- **左侧列出食材及用量**：左侧单次呈现食材名称、准确用量及必要准备说明（如切块、泡发）；
- **从左向右阅读加工顺序**：横向以时间与工序推进为轴，从左向右平视阅读工序演进；
- **区域合并表达汇合**：通过食材行的延伸、相邻行单元格区域合并与内部网格线终止，直观表达食材何时加入、如何汇合，**无需在格内重复书写食材清单**；
- **简短动作与关键参数**：通过准确简短的烹饪动作名称（如“滑炒盛出”、“炒糖色”、“小火焖炖”）与关键参数（火候变化、操作耗时、关键温度），快速获取核心决策依据；
- **关键流程变化清楚呈现**：对盛出暂存、回锅合炒、同锅等待、换锅等关键厨房事件，用清晰的走廊或短标签如实表达，确保流程完整不失真。

## 二、纠正此前设计偏移与核心原则

### 1. 废止的旧设计（文字灌水偏移）
此前为追求“完全零基础新手看图即可下厨”，向主图注入了大量冗余标注：
- `加入: 原料列表`（在单元格内再次罗列所有食材名）
- `承接: 半成品`（文字重复说明上游产物）
- `产出: 半成品`（文字重复说明当前阶段半成品）
- `状态: 完整句子`（在单元格内堆砌长达三四十个字的操作说明与判断标准）

### 2. 新的核心设计原则
1. **结构能够表达的关系，不再用文字重复说明**：
   - 食材行向右延伸并被某个工序单元格合并，空间结构本身已经表达“该食材在此步加入并参与处理”，主图动作单元格不再罗列“+ 放入: 白糖、植物油”；
   - 焯水后主料流向下游炖煮工序，连接与相邻关系本身已经表达物料流转，主图不再打上“承接: 焯透五花肉”、“产出: 焯透五花肉 ➔”等繁冗字样；
2. **只有结构无法清楚表达、且影响流程理解的关键信息，才增加短标记**：
   - 牛肉滑炒后盛出暂存，中间空出锅具留底油炒芹菜，稍后牛肉再回锅——这种脱离主干锅具、稍后汇入的关键事件，无法单靠紧邻网格表达，必须保留清晰的走廊连线与“盛出暂存”短标记；
3. **完整流程不等于详尽教程**：
   - 盛出、回锅、换锅、分批加入等关键操作事件必须保留，绝不能为减少文字而粗暴压缩工序导致流程失真；
   - 但完整的操作手法、火候微调技巧、准出判断句式属于详情层，不堆砌在主图内。

## 三、“完整数据—精简主图—详细说明”三层标准

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 完整数据层 (Domain Model: VisualRecipeV3)                 │
│    - 真实食材/量词/准备说明 (ingredients)                    │
│    - 严格依赖拓扑 (dependencies: material / order / legacy)  │
│    - 完整操作指导 (note / notes)                             │
│    - 达成准出条件 (completionState)                          │
│    - 阶段半成品 (outputItem)                                │
│    - 子配方成分与调制 (formulas)                             │
│    - 工序终点职责 (finalBlock.role: operation / outcome)     │
│    - 来源定位与核验状态 (provenance / dataReview)             │
│    - 估算与不确定性说明 (dataReview.assumptions)              │
└──────────────────────────────┬──────────────────────────────┘
                               │ 投影与过滤
         ┌─────────────────────┴─────────────────────┐
         ▼                                           ▼
┌────────────────────────────────┐ ┌────────────────────────────────┐
│ 2. 主图表达层 (Main Diagram)    │ │ 3. 详情层 (Details Layer)      │
│    - 食材名称、用量、简要准备  │ │    - 完整展开的操作指导句子    │
│    - 简短动作与次级副标        │ │    - 详细准出条件与观察要点    │
│    - 必要火候、温度与耗时      │ │    - 半成品产物完整流转说明    │
│    - 区域合并与连接结构        │ │    - 复合配方展开与调制时机    │
│    - 关键暂存、回锅短标记      │ │    - 来源依据、估算说明与待核实│
│    (单屏速览，零无意义文本)    │ │    (触屏点击 / 键盘 Tab+Enter)  │
└────────────────────────────────┘ └────────────────────────────────┘
```

### 1. 完整数据层 (Domain Model)
保存真实且细粒度的领域信息。绝不为主图视觉精炼而反向裁剪或删除具有学术/烹饪价值的数据字段（如 `completionState`、`outputItem`、`note` 等必须完整保存在数据对象中）。

### 2. 主图表达层 (Matrix Flow Card: Table / Branch Flow)
主图专注于二维拓扑的结构化表达：
- **食材区**：名称、份量、简明预备（如“切丝”）；
- **动作区**：动词主标（如“滑炒盛出”）、英文副标（如有）、火候/耗时/温度参数（如“中火 3m”）；
- **关系区**：连续合并边框、等待延续虚线行、暂存回锅虚线走廊或显式依赖箭头。
- **信息极简**：取消主图默认显示“加入：...”、“承接：...”、“产出：...”、“状态：...”。

### 3. 详情层 (Details Modal & Step List)
承载所有深层教学与说明内容：
- 用户点击任意工序单元格即可弹出对话框，查看该步的“完整操作指导”、“达成准出状态”、“关联食材清单与用量”、“产出半成品”；
- 页面底部提供全步骤操作指导抽屉；
- 保证无障碍键盘访问（Enter/Space 展开、Tab 焦点圈禁、Escape 退出并恢复焦点）与移动端触控友好。

### 4. 工序与终点的职责边界

`actionBlocks` 是食谱实际烹饪流程的完整事实源。每一个需要按顺序执行的动作都必须进入 `actionBlocks`，包括焯烫、盛出暂存、回锅、调味、收汁与装盘；不得把遗漏的实际动作藏在风味文案或结果说明中。

`finalBlock` 必须明确声明一种职责：

- `role: 'operation'`：终点本身仍是一个尚未在 `actionBlocks` 中执行的真实操作，例如“入炉烘焙 170°C 35m”。它占据工序表的一列，并必须提供可执行的动作标题；
- `role: 'outcome'`：所有操作已经由 `actionBlocks` 完整表达，终点只标记流程结束。主图仅显示紧凑的“完成”端点，不再生成一整列；
- 口感、色泽、风味写入 `resultDescription`，装盘、静置、趁热或放凉提示写入 `servingInstructions`，营养说明写入 `recipe.tips`；这些内容都不能冒充操作步骤；
- `finalBlock` 不得与最后一个 `actionBlock` 重复。若“文火慢炖”已是最后一个工序，终点不能再次显示“文火慢炖”；若烘焙尚未建成工序，则可保留为 `operation`。

## 四、统一主图视觉规范

两种视图（连续工序表与分支流程图）必须共享同一套设计 Token 与信息层级：

| 元素分类 | 视觉 Token / 规格 | 视觉规范与约束 |
| :--- | :--- | :--- |
| **画布底色** | `canvasBg: #FDFBF7`, `paperBg: #FFFFFF` | 温暖、素雅的纸质建筑感底色，非刺眼纯白。 |
| **外围与结构线** | `outerBorder: #CBD5E1` (1.5px), `gridLine: #E2E8F0` (1.2px) | 中性高级灰建筑感细线，杜绝粗笨绿色实线与杂乱多层描边。 |
| **食材呈现** | 份量 `#047857` (700加粗), 名称 `#0F172A` (600), 预备 `#64748B` (常规) | 左侧单次呈现。同一原料分次使用时保留各自明确份额（如 5g焯水、10g爆香），严禁错误合并。 |
| **动作主标题** | `#0F172A` (font-size: 13.5px, font-weight: 800) | 深黑突出。不机械限制为 2~4 字，“滑炒盛出”、“回锅合炒”等关键流程动作绝不删减。 |
| **英文副标** | `#64748B` (font-size: 10.5px, font-weight: 500) | 弱化呈现。原数据有则展示，无则留空，严禁自动补译或截断。 |
| **关键参数** | `#B45309` (暖琥珀色, font-size: 10px, font-weight: 700) | 火候、温度、操作耗时。火候变化按阶段表达（如“小火融糖转中火上色”）。推断时间标记“估”。不将步骤时长之和与总耗时混为一谈。 |
| **暂存与回锅** | `#059669` (走廊边框/短标记, font-size: 9.5px, font-weight: 700) | 走廊使用 `#F0FDF4` 浅绿底与绿色虚线，清晰指示跨列回锅。 |
| **操作型终步** | `#065F46` (font-size: 14px, font-weight: 800) | 仅用于仍需执行的真实操作（如“入炉烘焙”），占据工序列并显示温度/时间。不得与上一动作重复。 |
| **结果型终点** | 紧凑 `完成` 端点，最大约 `80×48px` | 只表示流程结束，不占据整列。口感、色泽、风味、营养说明不进入标题。 |
| **显式连线** | 物料边 `#059669` (实线), 时序边 `#64748B` (虚线) | 箭头精巧微小，线条平滑。 |

## 五、两种布局共享同一标准

PostSoma Kitchen 提供两种渲染排版视图：**连续工序表 (Continuous Process Table)** 与 **分支流程图 (Branching Flow Chart)**。

1. **布局不同，事实与标准完全一致**：
   - 模式切换仅改变空间排布（网格合并 vs 自由分支），**绝不改变食谱事实、依赖拓扑、参数或内容含义**；
   - 分支模式是正式视图，**全面废弃旧版绿色粗描边与红色大标题**，与连续工序表共享同一套中性建筑感设计 Token；
   - 页面与导出（SVG / PNG）严格使用同一套排版引擎与渲染参数。
2. **连续工序表准入硬性约束**：
   - 依赖必须已明确（禁止 legacy 旧依赖或非法格式依赖进入表格）；
   - 食材行必须严格连续（禁止跨行跳跃吸纳无关原料）；
   - 同一阶段内工序行绝对互斥（零实体重叠）；
   - 暂存跨列走廊在中间阶段必须具备空闲通道。
3. **安全降级机制**：
   - 任何不满足连续表格准入条件的食谱，系统**安全降级为分支流程图**，并向开发/用户提供清晰的模式说明，绝不为了绘制表格而虚构依赖或扭曲食材顺序。

### 分支流程图的专属职责与排版契约

分支流程图不是连续工序表的另一套皮肤。它只负责表达连续合并单元格无法诚实表达的拓扑事实：并行准备、半成品暂存、跨阶段回锅、多路物料汇合以及只约束先后而不传递物料的设备等待。

- 左侧食材保持单次呈现。每项食材只在**首次进入加工流程**时连接一次；进入流程后的流转由工序依赖边表达，禁止在后续每个节点重复画成“再次加入”；
- 右侧动作区采用有向无环图。节点横坐标由拓扑深度决定，纵坐标靠近首次加入食材的重心，同层节点通过独立车道消除碰撞；
- 动作节点高度只由内容决定，最低 `64px`。食材跨度由卡片左侧输入总线与端口表达，严禁把节点高度绑定为跨行包络高度；
- 动作区不得绘制贯穿全高的表格列边框。拓扑阶段只允许使用无描边、低对比度的浅色底板提示阅读节奏；
- 食材等待路径使用浅灰点线，接入总线与明确端口使用绿色实线；物料依赖使用翠绿实线箭头，设备/时序依赖使用灰蓝虚线箭头；
- 只显示会改变操作理解的边标签，例如“暂存牛肉”“同锅留底油”“回锅”。“物料流动”“承接前序处理物”等可由结构直接表达的通用标签必须隐藏；
- 边标签必须通过卡片碰撞检测。没有安全位置时隐藏主图标签，完整语义保留在 `<title>`、详情弹窗和步骤清单中；
- 所有没有下游动作的终端节点必须通过箭头连接结果型“完成”端点，终点不得孤立悬浮；
- 鼠标悬停或键盘聚焦食材时，高亮其首次接入节点及全部下游；聚焦动作时，高亮其上下游上下文，其余元素降级显示。静态导出仍须完整表达全部路径；
- 页面画布与 SVG/PNG 导出必须消费 `buildV3MatrixLayout` 的同一份节点、端口、路径与标签坐标，禁止两个渲染端分别推算几何。

## 六、取数与版本一致性契约

1. **单一度量事实源**：
   - 页面画布 (`Canvas`)、详情对话框 (`Modal`)、移动端视图 (`Mobile`) 以及导出 (`Export PNG/SVG`)，必须严格接收并消费**当前选中的同一个 VisualRecipeV3 对象实例**；
   - 导出时严禁重新发起异步请求从存储或网络读取可能不同步的数据。
2. **来源与版本标识**：
   - 区分预置模型预览 (`source=local`) 与持久化发布模型 (`getPublishedRecipeById`)；
   - 在开发与编辑环境中提供低侵入的版本指纹（如 `contentVersion` 或数据哈希），便于复现与审计；
   - 绝不以强制本地优先掩盖线上版本差异，绝不自动静默发布未核实草稿。

## 七、数据库事实可信度与准入标准

### 1. 发布状态不等于事实核验

- `status: draft | published` 只描述数据是否对访客可见；
- `dataReview.overall` 才描述食谱事实所处阶段：`unreviewed`、`modeled`、`transcribed`、`source_verified`、`kitchen_verified`；
- 已发布食谱仍可能处于待核对状态。界面和报告不得把“已发布”写成“配方已验证”。

### 2. 可复查来源

- `provenance` 记录来源类型、标题、作者、页码/章节/配方编号或 URL；
- 只有书名而没有可定位出处，只能证明资料归属，不能证明食材、用量、工序已经逐项核对；
- 声明 `source_verified` 必须同时提供可定位出处、核验人和核验日期；声明 `kitchen_verified` 必须提供核验人、日期与实测证据。

### 3. 分项核验

`dataReview` 分别记录 `ingredients`、`quantities`、`topology`、`heatAndTiming`。整体核验等级不得高于任一分项；任何分项尚处于建模或待核对状态时，系统必须阻断“整体已核验”的声明。

### 4. 自动化可修与必须人工裁决的边界

- 可自动修复：非法枚举归一化、重复显示文本清除、旧字段兼容投影、确定性的悬空/自引用/环路检测；
- 必须人工裁决：缺失克数、复合调料拆分、后续步骤究竟是 `material`、`order` 还是独立并行、火候与耗时、来源页码、厨房实测结论；
- 自动化脚本不得用“适量”、默认克数、相邻阶段或同一锅具等启发式规则补造事实。

### 5. 本地与云端内容对比

- 比较必须递归到食材、工序、依赖、配方、前置条件与终点块，不能只比较数组长度或浅层哈希；
- 单纯的食材显示顺序变化与实质配方/拓扑变化必须分开统计；
- `provenance` 与 `dataReview` 属于治理元数据，不应被误报为烹饪内容变化，但必须由独立审计报告跟踪；
- 未完成人工事实审核前，只生成迁移提案和 Dry Run，不自动覆盖 Supabase。
