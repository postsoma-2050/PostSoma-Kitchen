# Matrix Flow Card 架构与数据诊断

审查日期：2026-09-14。静态范围：当前工作区 `chineseHealthyRecipes.ts` 102 道食谱。
云端范围：使用本地公开连接配置只读查询 cn-59，返回 `content_version=2`；食材、两道工序与终点语义和本地一致。未读取其他云端食谱，未写入数据库。

结论：数据语义需要修复，布局模型也需要升级。不能靠 CSS 或字符串去重修复缺失的配方、用量与工序；不能靠删掉真实食材引用解决卡片跨行。

代码证据：

- `src/data/chineseHealthyRecipes.ts:3041`：真实原始对象，`amountText` 为调料名单；上浆、滑散、盛出和爆香、炒菜、回锅被压入两个动作；食用油出现在指令中却未进入食材表。
- `src/types/recipeV3.ts:69`：实际名称是 V3ActionBlock/V3Ingredient/V3FinalBlock，并非交接文档中的简写。用量、火候、时长、动作编码、finalBlock 等允许缺省，部分枚举与 string 联合退化为自由字符串。
- `src/types/formula.ts`：已经支持 marinade/sauce、配料数值、制作步骤、prepActionBlockId、usedActionBlockIds。不能声称系统完全没有腌料或碗汁槽位；实际存在却很少使用。
- `src/utils/matrixFlowLayout.ts:129`：把 ingredientIds 的 min/max 行当作实体矩形边界；非连续关联被变成连续覆盖。
- 同文件约 305 行：高度按跨度行数计算；终点也被设置为整表高度。约 380 行：缺少显式依赖时按行区间相交推断下游，不能保证烹饪因果。
- `RecipeFlowCanvasV3.vue:137`：直接拼接 amountText + name；151 行明确仅用列位置表达顺序。副标题不做本地化选择。instructions 主要进入 title，触屏用户缺少显性的核心指导。
- `RecipeFlowCanvasV3.vue` 的 isColdFinal 把 serve 与 raw 都当作冷食，并显示「免加热 / 拌匀即享」。热炒菜最后装盘会因此产生错误提示，必须将装盘操作和冷热分类分开。
- `src/utils/taxonomyMatcher.ts` 已检查缺失依赖、自引用与循环；但空依赖通过，不理解调味料名单、物料消耗与状态。
- `scripts/auditPresets.ts` 自己明确声明不证明烹饪事实，并在审计前 normalize。完整度不是可信度。另有写死「23 道」的旧说明与动态计数不一致。
- `tests/domain/flowGraph.test.ts:135` 明确要求画布不出现路径/编号；导出也有「不得渲染依赖线」断言。这是既有设计约束造成的退化，不是简单漏写 v-for。新分支模式须更新对应契约，保留旧模式兼容测试。
- `src/utils/exportFlowCard.ts` 独立生成 SVG，重复了文字与终点呈现逻辑。升级不能遗漏导出链路。

这些证据支持「有结构框架，但大量内容是压缩摘要式建模，尚未达到可执行烹饪协议」；不能证明是哪段脚本生成、谁人工随意填写、是否忠于原书。该数据文件历史只见一条整体提交，缺少逐菜来源与试做记录。

## 2. 数据 / 视图责任矩阵

| 问题 | 数据/领域必须负责 | 视图必须负责 |
|---|---|---|
| 名称与用量互抄 | 原料原子化；用量独立；缺量标 unknown | 名称、用量分列；旧数据可去掉完全重复的展示片段并报告问题，禁止回写 |
| 混合全部调料 | 按实际加入阶段建立 portion；混合物用 formula；备料集合用 group | 折叠为「上浆料·4项」并可展开；折叠不改变实际依赖 |
| 英文直译 | 迁入按 locale 索引的 translations；纠正错误翻译 | 默认展示当前语言；不靠菜系或英文正则裁剪所有文本 |
| 形容词充当动作 | operation + label 是动作；expectedResult 是状态 | 动作主标题；结果说明次级文本；具体操作可直接阅读 |
| 工序不完整 | 拆开改变物料状态、容器或锅具占用的关键动作 | 支持分支、汇合与顺序约束，不能从文案猜步骤 |
| 板砖覆盖全行 | ingredientIds/inputs 不得为了图形而删改 | 关联范围画端口/细线；卡片高度只由内容决定 |
| 缺失/循环/悬空依赖 | 保存/发布前结构校验；错误定位到字段 | 编辑态错误占位；阅读态降级文字流程，不伪造箭头 |
| 同一炒锅并行 | 显式 after/resource 约束 | 用虚线与等待说明表示，不暗示牛肉流入炒菜步骤 |
| 热菜装盘被当冷食 | 分离 cookingMethod、finish.operation 与结果属性 | 不从 serve 推导「免加热」 |

允许的防御：空白归一、XML 转义、未知枚举占位、长文本换行、容器滚动、错误边界。禁止的静默修复：把缺失用量改成「适量」、按名称猜类别覆盖数据、删掉环路边、按相同行推断真实物料、把缺失上游变为已完成。

发布校验必须严格，但公共阅读界面不应裸抛异常白屏；编辑器展示错误路径、原始值与修复建议。区分「保留源数据」和「强迫用户阅读坏格式」。

## 3. 推荐领域模型

三类事实分开存储：

1. 原料与分次用量：ingredient 是物品；portion 是本次操作实际加入的一份。两次加油是两个 portion，购物清单按 ingredientId 汇总，未知量不能参加精确营养/倍率计算。
2. 物料状态：每道动作消费 portion 或上游 output，产生带 location 的新 output。后续合炒引用「暂存牛肉」，不重复消费原始 200g 牛肉。
3. 控制顺序：after 表示锅具释放、等待、准备完成，与物料边分离。stage/坐标只属于视图提示，不是事实来源。

formula 是可执行子配方（配料份额 + 制作动作 + 产出），group 是同阶段备料集合。爆锅小料未混成一种酱，不能仅为了折叠视觉把它当万能碗汁。配方项与购物表共用原料引用，禁止双算。

单产出的简化模型足够演示本菜；分一半酱汁、取部分高汤等需要显式 split 操作、多产出及数量守恒。不要把同一 output 任意接两条消费边。废弃物也应作为有记录的输出或丢弃动作。

出版质量另设 evidence/verification：来源位置、试做者、日期、厨具/灶具、配比、时长范围、操作终点、实测结论。原来的 complete/published 不能继续等同于实测；升级后的食谱缺失关键事实时保持草稿。

## 4. 完整前后示例与算法

- `cn59-before.ts`：本地对象完整快照，全部字段保留。
- `cn59-after.ts`：完整新类型与食谱对象，包含 11 种原料、12 份分阶段用料、1 个上浆配方、1 个小料组、10 个动作和装盘终点。
- `branch-layout.ts`：可运行的语义编译、Kahn 拓扑排序、共享器具顺序验证、内容决定高度、同层泳道碰撞处理、相邻列折线与跨列暂存线。
- `BranchCanvasExample.vue`：SVG 连线/箭头、主次文本、安全错误边界、键盘可滚动区域、完整文字替代流程。
- `verify-example.ts`：对应验证。

重构后仍是待核实草稿，不是「规范实测完成」：原数据只给了牛肉/芹菜各 200g；调味料、油量、淀粉水比例均未提供，旧两段各 2 分钟也不能自动分摊。新准备步骤、配方混合方式、分次用油是合理建模提案，需要回查与试做。标题不再携带未建立证据的功效承诺。

算法顺序：先验证引用和 DAG → 按物料与控制边算拓扑层 → 按语义泳道放节点 → 按文本测量高度 → 同层冲突下移而非右移 → 为每条边分配端口/通道 → 绘制连接与节点。

示例有意使用简单确定性布线；保证本测试中不穿卡，不保证全局最少交叉，不是完整 Sugiyama 实现。复杂图应增加重心扫掠减少交叉、通道拥挤处理与折叠子图。拓扑列只表示先后，耗时另行显示。不能通过拖动视图坐标改写事实依赖。

Vue 参考的原料入口以文字明细列出，不是完整的交互式配方折叠编辑器。正式接入时为原料行/配方组产生来源端口；折叠只合并视图端口并保留内部真实边，使用同一布局输出供页面与导出消费。

## 5. 视觉标准

- 原料展示「名称 | 用量」一次；处理方法放准备说明。单位、数值、原料名各司其职。
- 默认中文单语言；英文翻译不是必填副标题。温度单位、必要设备型号等不是冗余翻译。
- 动作标题使用动词短语；一块表达一个可观察的状态变化。切菜等细节可在备料子图中折叠，盛出、回锅与汇合不可隐藏。
- 实线 = 物料，虚线 = 操作先后；都有箭头/文字说明，不能仅靠颜色。保留「暂存牛肉」到「回锅合炒」的直接物料边。
- 卡片高度与关联多少食材无关；禁止将 minRow…maxRow 当实体。非连续原料通过细线/端口汇聚，必要时高亮关联行。
- 终点主标题「出锅装盘」；次级「关火，移入餐盘」；第三层「目标口感：牛肉滑嫩，芹菜爽脆」。目标口感不充当已验证事实。
- 不从 serve 推导冷食。烤制/炖制若尚未完成，应是实际加热动作节点，不能被统一装盘替换而丢失时温。
- 桌面画布支持横向浏览；移动端优先顺序卡片加汇合标签，不把整张图缩到难读。完整指令不能只藏在 hover title。
- 默认卡片以 14px 标题、12px 辅助信息为参考；随阅读环境增大，正文不依赖微字。折叠控件需可键盘操作、有可访问名称与展开状态。

## 6. 102 道可执行升级策略

**阶段 A：建立证据与基线。** 原始对象先审计，再 normalize 后审计，分别报告。保存版本、内容 hash、发现路径、严重度、规则版本、来源范围。当前脚本是只读预检，复合食材与缺依赖只产审核候选；--strict 仅阻断重复名称用量候选，不能替代完整发布闸门。

**阶段 B：人工确认语义。** 优先 cn-59 与存在多次回锅/子配方的菜。核查 21 项重复、146 项混合候选；回查来源补量，拆分加入阶段，记录待确认项。不能按连接符批量拆分后随便均分用量，更不能因为 0 个显式依赖就自动把所有动作串联。

**阶段 C：版本化草稿。** 使用独立 schemaVersion，新读写器显式分派；不可把新对象标成 3.0 喂给旧 isV3Recipe。V3→新模型无法确定的信息进入 unknown，保留原对象。原有 formulas 可以转换，但其 prep/used 关联也需要人工复核。新增草稿不直接继承 published。

**阶段 D：自动闸门。**

| 类别 | 检查 | 策略 |
|---|---|---|
| 结构 | ID 唯一，引用存在，枚举合法，有限正数用量，合法时长范围 | 阻断 |
| 配方 | 子配方制作/消费一致，不重算购物量，公式引用无环 | 阻断 |
| 工序 | 无环，所有成品可追溯，不重复消费，物料无意外丢失 | 阻断 |
| 资源 | 同锅具不能无序并行，盛出有明确输出/容器 | 阻断 |
| 文案 | 名量互抄、英文模板、副标题冗余、终点疑似纯形容词 | 确定错误阻断；语言启发式进入人工复核 |
| 事实 | 缺关键配比/熟度/来源/试做记录 | 不授予对应验证等级；实测发布流阻断 |
| 视觉 | 文本边界、卡片碰撞、箭头入/出端口、连线穿卡、窄屏与导出 | 新模式回归测试 |

代表性夹具必须含：非连续食材行、仅消费上游输出的动作、同锅先后/双锅并行、先盛出再回锅、腌料/碗汁两支线、长中文标题、缺译文、空草稿、环/悬空引用、分份取用。

**阶段 E：迁移发布。** 导出完整旧 content + content_version → 为每道生成审核 patch（beforeHash、after、证据、规则版本）→ dry-run 报告 → 审核与试做 → 先试点再分批。数据库仍经 Repository/RPC 保存，携带读取时的乐观锁版本；版本冲突停止该条，重新加载后合并，不覆盖用户编辑。保存成功后读回核对 hash 与新版本；重复运行按 afterHash 跳过。一次 RPC 的原子性只覆盖一次食谱保存，不代表 102 道整体事务。

回滚通过 revision 内容创建新的恢复版本，不倒退版本号或删除历史。只改静态 TS 文件不会修复已导入云端/缓存的对象；迁移成功后需要使缓存失效或刷新。新旧模式并行期间共享 Presenter/布局输出，网页与 exportFlowCard 的分页都保留跨页依赖标记，不能对子集食材重新猜图。
